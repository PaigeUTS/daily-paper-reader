## 摘要
现代AI服务日益依赖NPU进行常规推理和大语言模型服务。然而，当前的NPU部署通常将物理设备直接暴露给应用程序，这限制了运行时对调度的控制，并使得难以根据阶段级工作负载行为调整执行。这一限制在LLM服务中尤为明显，其中预填充阶段是计算密集型的，而解码阶段通常受限于内存带宽和KV缓存访问。静态预填充-解码（PD）分离减少了阶段干扰，但可能引入资源不平衡和不必要的数据移动。我们提出了FlexNPU，一个用于昇腾NPU的透明用户空间虚拟化层。FlexNPU拦截AscendCL API，并通过每设备守护进程路由NPU操作，将未修改的应用程序与物理NPU设备解耦，无需修改模型代码、AI框架或NPU驱动。这一运行时边界使得FlexNPU能够虚拟化NPU对象、控制算子调度，并支持面向LLM服务的阶段感知调度。特别是，FlexNPU实现了动态PD共置，根据预填充和解码互补的资源特性自适应调度。我们在华为昇腾NPU上实现了FlexNPU，并针对典型LLM工作负载进行了评估。与直接NPU透传相比，FlexNPU没有引入可衡量的推理开销，并且在某些场景下略微提高了吞吐量。在384卡昇腾910C部署的DeepSeek-R1上，FlexNPU相比静态PD分离将吞吐量分别提升了5.15%和26.33%。对于Qwen2.5-7B，与静态PD共置相比，FlexNPU在测试的工作负载上保持了相当的吞吐量，同时将TTFT降低了超过92%，而TPOT几乎不变。这些结果表明，透明NPU虚拟化是实现高效且响应迅速的LLM服务的实用基础。

## Abstract
Modern AI serving increasingly relies on NPUs for conventional inference and large language model serving. However, current NPU deployments commonly expose physical devices directly to applications, which limits runtime control over scheduling and makes it difficult to adapt execution to phase-level workload behavior. This limitation is particularly evident in LLM serving, where the prefill phase is compute-intensive while the decode phase is often constrained by memory bandwidth and KV-cache accesses. Static prefill-decode (PD) disaggregation reduces phase interference, but can introduce resource imbalance and unnecessary data movement. We present FlexNPU, a transparent user-space virtualization layer for Ascend NPUs. FlexNPU interposes on AscendCL APIs and routes NPU operations through per-device daemons, decoupling unmodified from physical NPU devices without modifying model code, AI frameworks, or NPU drivers. This runtime boundary allows FlexNPU to virtualize NPU objects, control operator dispatch, and support phase-aware scheduling for LLM serving. In particular, FlexNPU enables dynamic PD co-location, which adapts scheduling between prefill and decode according to their complementary resource characteristics. We implement FlexNPU on Huawei Ascend NPUs and evaluate it with typical LLM workloads. Compared with direct NPU passthrough, FlexNPU introduces no measurable inference overhead and slightly improves throughput in some scenarios. On a 384-card Ascend 910C deployment of DeepSeek-R1, FlexNPU improves throughput over static PD disaggregation by 5.15% and 26.33%. On Qwen2.5-7B, compared with static PD co-location, FlexNPU maintains comparable throughput while reducing TTFT by over 92% across tested workloads with nearly unchanged TPOT. These results show that transparent NPU virtualization is a practical substrate for efficient and responsive LLM serving.

- **核心问题**：当前NPU（神经网络处理单元，如华为昇腾芯片）部署普遍采用“直通模式”（passthrough），将物理设备直接暴露给应用程序，导致运行时缺乏调度控制能力。这种模式无法适应LLM推理中“预填充（prefill）”与“解码（decode）”两阶段的互补资源特征（prefill计算密集、decode访存受限且依赖KV缓存）。静态PD分离（将两阶段部署在不同设备上）虽然减少了干扰，但会引发资源失衡（prefill设备内存带宽利用率低，decode设备计算资源闲置）和额外的KV缓存移动开销。
- **整体含义**：为了在无需修改模型代码、AI框架或NPU驱动的前提下，实现对NPU执行的运行时控制，需要构建一个**透明的用户空间虚拟化层**，以支持动态PD共置调度，从而在保持高效性的同时提升LLM服务的吞吐量与响应速度。

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：在AscendCL（昇腾计算语言，NPU运行时API）边界插入一个用户空间虚拟化层，通过拦截AscendCL API调用，将操作路由到每设备守护进程，实现应用与物理NPU的解耦。在此基础上，利用虚拟化层收集的运行时信息，实现阶段感知的动态PD共置调度。
- **关键技术细节**：
  - **透明拦截与代理**：使用`LD_PRELOAD`注入客户端库，拦截AscendCL中的关键API（设备管理、内存分配、流/事件管理、同步、模型/算子执行等）。客户端将请求描述符（操作类型、虚拟句柄、元数据）转发给守护进程，大张量数据不经过控制路径（仅传递句柄和元数据）。
  - **句柄虚拟化**：为每个应用维护虚拟NPU对象（虚拟设备、上下文、流、事件、内存指针），守护进程维护虚拟到物理资源的映射，实现透明调度。
  - **轻量级运行时分析器**：收集算子执行时间、排队延迟、内存分配、流使用情况、阶段级吞吐量等统计信息，用于指导调度决策。
  - **动态PD共置调度**：将prefill和decode作为独立逻辑实例运行，通过守护进程维护各自的操作队列，根据运行时信号（待处理操作数、最近执行时间、内存带宽压力、活跃序列数、NPU队列占用率等）动态调整两阶段的执行比例。策略不依赖硬件空间分区，完全通过用户空间调度和流调度实现。
- **算法流程（文字描述）**：
  1. 应用调用AscendCL API → FlexNPU客户端拦截并封装请求。
  2. 客户端通过共享内存通道将请求转发给守护进程。
  3. 守护进程解析请求，将虚拟句柄翻译为物理资源，根据当前调度策略将操作插入prefill或decode队列。
  4. 守护进程根据最近执行延迟、内存带宽利用率等指标，动态调整两队列的调度权重（例如：当decode接近带宽饱和时，增加prefill执行机会；当decode积压严重时，增加decode的调度份额）。
  5. 操作被异步派发到物理NPU执行，守护进程负责同步和回调。

## 6. 主要结论与发现

- **性能影响极小**：FlexNPU虚拟化层带来的端到端推理开销可忽略不计，甚至在DeepSeek-R1-Distill-Llama-8B上吞吐量提升1.08%（由于异步代理设计减少等待）。
- **相对于静态PD分离**：在384卡DeepSeek-R1部署中，动态PD共置在1K-4K负载下吞吐量提升5.15%，在1K-1K负载下提升26.33%。
- **相对于静态PD共置**：在Qwen2.5-7B上，FlexNPU在四种负载下吞吐量相当或略有提升（-0.52%～+3.57%），但**大幅降低TTFT**：从数百秒降至亚秒级（降幅92%～99.93%），同时TPOT几乎不变（变化在-2.12%～+0.90%）。表明静态共置存在严重的“头部阻塞”问题（prefill和decode争用资源导致首token延迟极大），FlexNPU通过阶段感知调度有效缓解。
- **核心发现**：透明NPU虚拟化是实现高效LLM服务的实用基础，动态PD共置能够在不修改应用代码的情况下，同时优化吞吐量和响应延迟。

## 7. 优点

- **透明性**：无需修改模型代码、AI框架或NPU驱动，通过`LD_PRELOAD`注入即可工作，部署成本低。
- **低开销**：仅拦截少量稳定API，元数据轻量传递，大张量不走控制路径，确保推理性能无损。
- **实用性**：针对昇腾NPU原生设计，不依赖硬件空间分区，可部署于现有集群。
- **阶段感知调度**：充分利用prefill和decode的资源互补性，动态调整执行比例，避免固定分片带来的资源浪费。
- **实验充分**：覆盖两种模型尺度、多种负载特征、两种主流部署模式（PD分离与PD共置），并同时报告吞吐量和延迟指标（TTFT、TPOT），验证了方法的普适性。
- **结果显著**：在大型MoE模型上吞吐提升26%，在小型密集模型上首token延迟降低两个数量级。

## 8. 不足与局限

  - 性能影响实验仅测试单一模型和固定batch配置（DeepSeek-R1-Distill-8B），缺乏更广泛模型和多种请求率的验证。
  - 未进行消融实验（如不同调度策略、不同时间片调整算法）来量化各设计选择的贡献。

- **可扩展性与可靠性**：

- **应用限制**：目前仅针对LLM推理的prefill-decode场景，对于其他AI工作负载（如CV、推荐系统）的适用性未探讨。
