## 摘要
多轮对话是LLM应用中的基础场景，广泛用于聊天机器人和AI代理。随着对话的进行，历史令牌不断积累。现有系统缓存其键值对以避免重复计算。然而，有限的GPU内存（HBM）容量通常迫使这些KV缓存被卸载到CPU内存或SSD，这使得随着上下文增长，KV缓存重载在延迟方面变得越来越昂贵。同时，受限的HBM容量也限制了最大推理长度，从而限制了对话中可支持的轮数。为了解决这两个挑战，我们提出了SwiftCache，一种协作推理系统，使异构模型能够在服务器内共享未充分利用的GPU内存和NVLink带宽。具体来说，KV缓存需求较低的模型将空闲GPU内存捐赠给存储高需求模型的前缀缓存，从而通过NVLink实现跨模型的KV缓存共享，并避免缓慢的PCIe传输。SwiftCache通过仅在本地GPU内存中保留当前活动层的KV缓存，进一步减少内存压力，从而实现更长上下文的推理。我们在真实工作负载上的实验表明，与vLLM和SGLang相比，SwiftCache将P99首次令牌生成时间（TTFT）降低高达69%，并将最大上下文长度延长高达3.98倍，同时对共置模型的干扰最小。

## Abstract
Multi-turn conversation is a fundamental scenario in LLM applications, widely used in chatbots and AI agents. As the conversation evolves, historical tokens accumulate continuously. Existing systems cache their key-value (KV) pairs to avoid redundant computation. However, limited GPU memory (HBM) capacity often forces these KV caches to be offloaded to CPU memory or SSD, making KV cache reloads increasingly costly in terms of latency as the context grows. Meanwhile, the constrained HBM capacity also limits the maximum inference length, thereby restricting the number of turns that can be supported in a conversation.   To address these two challenges, we propose SwiftCache, a collaborative inference system that enables heterogeneous models to share underutilized GPU memory and NVLink bandwidth within a server. Specifically, models with low KV cache demand donate idle GPU memory to store the prefix cache of high-demand models, allowing cross-model KV cache sharing over NVLink and avoiding slow PCIe transfers. SwiftCache further reduces memory pressure by keeping only the KV cache of the currently active layer in local GPU memory, thereby enabling longer-context inference. Our experiments on real-world workloads show that SwiftCache reduces P99 time-to-first-token (TTFT) by up to 69% and extends maximum context length by up to 3.98x compared to vLLM and SGLang, with minimal interference to co-located models.

# SwiftCache 论文详细总结

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：多轮对话场景下，LLM 服务面临两大挑战：一是随着历史 token 累积，KV 缓存被卸载到 CPU/SSD 后，通过 PCIe 重载延迟极高（可达总延迟的 86.2%）；二是有限的 GPU HBM 容量限制了最大推理上下文长度（例如 LWM-1M-Text 在 96GB H20 上只能处理 160K token，远低于标称的 1M）。
- **整体含义**：现有系统（vLLM、SGLang）采用层次化缓存卸载策略，但未能充分利用服务器内多 GPU 间的闲置内存和高速 NVLink 带宽。本文旨在通过跨模型协作共享 KV 缓存和优化内存管理，实现低延迟、长上下文的 LLM 推理服务。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 核心思想
- **异构模型协作**：将高 KV 缓存需求模型（长上下文对话）与低需求模型（如短文本摘要）同机部署，低需求模型捐赠空闲 GPU 内存给高需求模型，通过 NVLink 高速传输 KV 缓存，避免 PCIe 瓶颈。
- **活跃层缓存流式化**：只保留当前推理层的 KV 缓存于本地 GPU，其余层缓存存放到外部（其他 GPU），降低本地内存占用，支持更长的推理序列。
- **弹性缓存与块主元布局**：设计 O(1) 时间复杂度的缓存重分配机制，支持根据工作负载动态调整各模型缓存容量，避免传统层主元布局下的大量数据搬移。

### 关键技术细节
1. **Master-Worker 架构**：
   - Master：高需求模型，负责实际推理。
   - Worker：低需求模型，提供空闲 GPU 内存和 NVLink 带宽。
2. **Layer Stream Cache (LSC)**：
   - 仅在 Master 本地保留当前层的 KV 缓存（单层块），其余层的 KV 缓存通过 NVLink 从 Worker GPU 预取。
   - LSC 容量 = min(∑ Worker 可存单层块数, Master 本地可存单层块数)。
3. **Regular Cache (RC)**：
   - 若 LSC 未占满 Master 本地内存，则剩余内存用于存储全层 KV 缓存块（RC），提供零跨 GPU 延迟的访问。
4. **块主元布局 (Block-Major Layout)**：
   - 将 KV 缓存张量形状从 (n_layers, n_blocks, block_elems) 调整为 (n_blocks, n_layers, block_elems)，使得同一块索引的所有层数据连续存储，扩容或缩容只需在末尾追加/释放块，无需移动其他数据，时间复杂度 O(1)。
5. **最小弹性单元 (MEU)**：
   - 基于 Master 和 Worker 块元素数的最小公倍数 (LCM) 定义，确保缩放操作时内存对齐，避免浪费。
6. **Master-Worker 协调**：
   - Worker 通过 ScaleUp/ScaleDown 算法（依赖时间窗口历史请求长度）决定主动扩容或归还缓存，并通过 Coordinator 同步块表，实现动态平衡。

## 6. 论文的主要结论与发现

1. **延迟显著降低**：相比 SGLang (HiCache)，P99 TTFT 降低约 67% (ShareGPT) 和 69% (L-Eval)；相比 vLLM (LMCache)，降低约 54% 和 58%。
2. **上下文长度大幅扩展**：在不同 VRAM 下，最大上下文长度达到 vLLM w/ chunked prefill 的 1.58×～3.98×，是 vLLM w/o chunked prefill 的 1.81×～6.66×。
3. **对工作模型干扰极小**：Master 推理期间，Worker 的 TTFT 增加 ≤9.7%，TPOT 增加 ≤6.5%，主要消耗网络带宽而非计算资源。
4. **KV 传输开销可忽略**：在预填充阶段，加载/存储 KV 仅占总延迟的 <1.4%，通过计算与传输重叠可降至 <0.1%，99% 的请求加载时间 <11ms、存储时间 <6ms。

## 7. 优点

- **创新性**：首次提出跨异构模型的 KV 缓存共享方案，利用 NVLink 替代 PCIe，有效利用闲置带宽和内存。
- **优雅的设计**：Layer Stream Cache 和块主元布局的设计简洁且高效（O(1) 重分配），避免了复杂的数据搬移。
- **实用性**：与现有主流推理优化（连续批处理、PagedAttention、FlashAttention）无缝集成，且无需修改模型本身。
- **低干扰**：工作模型性能损失极小，适合多模型共存的商业部署场景。
- **实验充分**：涵盖多种 GPU 容量、模型规模、工作负载，对比了多个 SOTA 基线，且提供了详细的延迟分解和干扰分析。

## 8. 不足与局限

- **实验覆盖有限**：仅测试了 H20 GPU（96GB）环境，未在 A100、H100 等更常见的高端 GPU 上验证，通用性待确认。另外，仅使用 Qwen3 和 LWM 系列模型，未涵盖更多异构模型（如 MoE 架构的 DeepSeek）。
- **潜在偏差风险**：实验中选择的长上下文请求（>20K tokens）可能偏向于高缓存需求场景，未充分评估短上下文场景下的性能差异。
- **应用限制**：当前设计仅适用于单服务器多 GPU 环境（依赖 NVLink 直连），无法扩展到跨服务器集群，扩展性受限。论文也承认这是未来工作。
- **内存对齐开销**：MEU 机制虽保证了内存对齐，但可能引入少量内部碎片，论文未量化该影响。
- **弹性缩放粒度**：ScaleDown 依赖历史窗口最大值，可能过于保守，导致内存利用率不够高，且未考虑突发流量场景。
