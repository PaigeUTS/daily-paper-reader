## 摘要
编码代理是一种快速增长的LLM应用，以长时间运行的闭环会话方式执行，其中LLM生成与外部工具调用交替进行。然而，与聊天工作负载不同，其服务行为尚未得到广泛研究。我们通过收集真实世界编码助手轨迹的数据集来填补这一空白。我们的分析表明，编码代理会话重复重用大型前缀，并产生持续KVCache压力，传统LLM服务策略难以应对。基于我们的分析，我们提出了CacheWise，一种KVCache管理层，旨在改善编码代理工作负载的KVCache重用。CacheWise结合了前缀感知调度与基于工具调用元数据的轻量级预测指导的重用感知驱逐。在vLLM中实现并在收集的轨迹上进行评估，CacheWise将KVCache驱逐减少了最多2-2.6倍，并将总代理会话完成时间提高了最多3.5倍。

## Abstract
Coding agents are a fast-growing LLM application, executing as long-running closed-loop sessions in which LLM generations alternate with external tool calls. Yet, unlike chat workloads, their serving behavior has not been studied extensively. We address this gap by collecting a dataset of real-world coding assistant traces. Our analysis shows that coding agent sessions repeatedly reuse large prefixes and create sustained KVCache pressure that conventional LLM serving policies handle poorly.   Based on our analysis, we present CacheWise, a KVCache management layer that improves KVCache reuse for coding agent workloads. CacheWise combines prefix-aware scheduling with reuse-aware eviction guided by lightweight predictions from tool call metadata. Implemented in vLLM and evaluated on the collected traces, CacheWise reduces KVCache evictions by up to 2-2.6x and improves total agent session completion time by up to 3.5x.

### 论文核心问题与整体含义（研究动机和背景）

*   **核心问题**：当前主流的 LLM 服务系统（如 vLLM），其调度和 KVCache 管理策略是为聊天等传统工作负载设计的，无法高效地服务于日益增长的**编码代理（Coding Agent）** 这一新兴工作负载。
*   **研究背景与动机**：
    1.  **编码代理的工作负载特征独特**：与单轮或短期交互的聊天不同，编码代理是**长时间运行的闭环会话**。一个用户任务会触发多轮“LLM 生成 -> 工具调用（如运行代码、编辑文件） -> 结果返回 -> 下一轮 LLM 生成”的循环。
    2.  **现有策略的严重不匹配**：
        *   **FCFS 调度**：交错处理多个会话的请求，导致不同会话的 KVCache 在 GPU 内存中竞争，引发频繁的**KVCache 抖动**（反复驱逐和重计算）。
        *   **LRU 驱逐策略**：仅依赖过去的访问时间进行驱逐，无法区分一个即将完成工具调用的会话（KVCache 即将被重用）和一个将长期空闲的会话。因此，它常常驱逐“即将被重用”的 KVCache 块，造成不必要的开销。
    3.  **现有解决方案的局限性**：一些近期工作尝试优化代理工作负载，但它们紧密耦合了代理框架和 LLM 服务系统，不适合需要支持多样化客户端的通用大规模部署。
*   **整体含义**：要实现高效的编码代理服务，必须设计一个**工作负载感知**的 KVCache 管理层，该层能够理解“会话”的概念，并预测 KVCache 的未来重用模式。

### 论文提出的方法论：核心思想与关键技术

论文提出了 **CacheWise**，一个位于通用 LLM 服务系统之上的 KVCache 管理层，其核心是两大关键技术：

1.  **前缀感知请求调度 (Prefix-aware Request Scheduling)**：
    *   **核心思想**：在对请求进行批处理时，优先调度那些与当前 GPU 内存中 KVCache  有**最大重叠部分（即需要最少额外 KVCache 块）** 的请求。
    *   **技术细节**：对于编码代理工作负载，同一个会话的连续请求会共享一个巨大且不断增长的前缀。优先处理这些请求能最大限度地利用已有 KVCache，减少因分配新 KVCache 空间而驱逐其他会话块的可能性。
    *   **近似最短作业优先**：需要较少额外块的请求通常也较短，这不仅减少抖动，也近似实现了短作业优先（SJF）调度，有利于优化**端到端的会话完成时间**，这正是代理工作负载的关键性能指标。

2.  **预测性 KVCache 驱逐 (Predictive KVCache Eviction)**：
    *   **核心思想**：避免使用仅基于过往（LRU）的驱逐策略，而是预测每个 KVCache 块**未来被再次使用的时间 (τ)**，并优先驱逐那些预期未来被使用时间最晚的块（近似于 Belady 最优算法）。
    *   **关键技术细节**：
        *   **轻量级预测器**：CacheWise 利用每个请求附带的**工具调用元数据**（如工具名称 `bash`, `grep` 和其参数 `ls -la`, `pytest`）来预测工具的执行时长，从而推算出 KVCache 的重用时间间隔。
        *   **语义聚类**：工具的执行时长不仅与名称有关，更与参数高度相关。为了提高预测精度，CacheWise 使用**TF-IDF 将工具参数编码为向量**，然后通过 K-means 算法将具有相似参数的工具调用**聚类**，并基于每个聚类的历史执行时长分布来进行预测。
        *   **实现**：在 vLLM 中实现，用预测的 E[τ] 值替换 LRU 堆作为 KVCache 块的驱逐优先级。系统会定期（每 3 次引擎迭代）重新评估所有“未引用”块的 E[τ] 值并重建驱逐堆，以应对时间推移导致预测值过时的问题。
