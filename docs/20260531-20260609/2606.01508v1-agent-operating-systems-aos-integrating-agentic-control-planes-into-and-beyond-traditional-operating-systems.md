## 摘要
传统操作系统围绕确定性程序、显式控制流和人类启动的工作流设计。其核心抽象——进程、线程、系统调用、文件和权限——假设有限的行为和可预测的交互模式。代理式AI系统引入了一种不同的执行模型：长期存在、目标导向的实体，它们进行概率推理、动态调用工具，并根据反馈调整行为。尽管代理目前可以作为用户空间应用程序实现，但其执行特性在调度、内存和状态管理、安全性、可观测性和治理方面对操作系统边界造成了压力。本文引入了代理操作系统（AOS）的概念，这是一种将代理控制平面集成到现有操作系统中，或在某些模型中随时间逐渐接管选定操作系统职责的系统架构。我们提供了AOS的精确定义、明确的假设和非目标，以及将AOS职责结构化分解为调度器、上下文和内存管理、工具和能力注册表、策略和信任实施、以及可观测性和审计。我们分析了经典操作系统抽象对代理工作负载的局限性，提出了从用户空间运行时到分布式控制平面的集成模型，并将AOS概念映射到Linux和Windows原语。我们讨论了安全与保障影响，包括代理特定的威胁模型，并定义了强调确定性实施、可审计性和操作者可理解性的评估标准。目标不是完全取代操作系统，而是为代理计算建立一个严格的系统基础，使其在大规模下保持可控、可问责和安全。

## Abstract
Traditional operating systems were designed around deterministic programs, explicit control flow, and human initiated workflows. Their core abstractions processes, threads, system calls, files, and permissions assume bounded behavior and predictable interaction patterns. Agentic AI systems introduce a different execution model: long-lived, goal-directed entities that reason probabilistically, invoke tools dynamically, and adapt behavior based on feedback. While agents can be implemented as user-space applications today, their execution characteristics stress OS boundaries in scheduling, memory and state management, security, observability, and governance. This paper introduces the concept of an Agent Operating System (AOS), a systems architecture that integrates an agentic control plane into existing operating systems or, in some models, subsumes selected OS responsibilities over time. We provide a precise definition of an AOS, explicit assumptions and non-goals, and a structured decomposition of AOS responsibilities into schedulers, context and memory management, tool and capability registries, policy and trust enforcement, and observability and audit. We analyze limitations of classical OS abstractions for agent workloads, propose integration models from user-space runtimes to distributed control planes, and map AOS concepts onto Linux and Windows primitives. We present security and safety implications, including agent specific threat models, and define evaluation criteria that emphasize deterministic enforcement, auditability, and operator comprehensibility. The objective is not to replace operating systems wholesale, but to establish a rigorous systems foundation for agentic computation that remains controllable, accountable, and secure at scale.

# 论文总结：Agent Operating Systems (AOS)

## 1. 核心问题与整体含义（研究动机和背景）

- **问题**：传统操作系统（如 Linux、Windows）的核心抽象——进程、线程、系统调用、文件、权限——围绕确定性程序、显式控制流和人为启动的工作流设计，假定行为有界、交互可预测。而现代 Agentic AI 系统是长期存在、目标导向、概率推理、动态调用工具并自适应调整的实体，其执行特性在调度、内存/状态管理、安全性、可观测性和治理上严重挑战了 OS 边界。
- **动机**：当前做法将 Agent 简单视为调用 API 的应用程序，导致资源调度错位（Agent 进展依赖外部事件和工具延迟）、内存语义不匹配（Agent 状态包含上下文窗口、长期记忆、检索知识等不同生命周期和信任级别的数据）、安全不完整（工具调用需要作用域权限）、可观测性不足（需要决策谱系而非仅 CPU/内存指标）、治理缺失（安全策略必须在非确定性推理外确定性执行）。
- **整体含义**：若 Agent 成为一等计算实体，OS 边界应如何演变？论文提出 Agent Operating System (AOS) 作为结构化答案——不是取代现有 OS，而是在其上引入意图和治理作为一等调度和强制概念，实现“在边界处使自治性具有确定性”。

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：AOS 是一个系统软件层，通过扩展或重新解释经典 OS 职责来管理目标导向 Agent 的生命周期、执行、协调和治理，同时保持系统边界的确定性行为。分离三个平面：
  - **推理平面**：执行概率推理、规划（允许非确定性），被视为不受信任的。
  - **执行平面**：执行确定性工具调用、系统调用和副作用，在最小权限环境中运行。
  - **策略平面**：执行授权、风险检查、合规约束和预算控制，默认拒绝模糊情况，生成可审计决策及原因码。
- **关键技术组件**：
  - **Agent 生命周期管理器**：定义比进程状态更丰富的状态（创建、初始化、活动推理、等待事件、执行、挂起、终止），处理确定性终止语义（取消飞行中工具请求、撤销令牌、持久化最终审计闭包记录）。
  - **Agent 调度器**：优化目标进展而非 CPU 公平性，输入包括优先级/SLA、成本预算和速率限制、依赖图状态、风险态势等；输出包括推理分片、工具调用时机、是否需要人工审批、节流/暂停/隔离。
  - **上下文与内存管理**：定义四类内存（短期上下文、持久 Agent 内存、检索知识、执行记录），要求上下文构建确定性、检索集记录、过滤器确定性且可重现，支持基于策略的保留/删除。
  - **工具与能力注册表**：工具定义包含名称版本、输入模式、副作用分类、所需能力作用域、速率限制、确定性预检查、后条件、审计要求。能力必须明确、最小权限、可撤销。
  - **策略实施**：分层策略（静态授权、能力约束、上下文策略、风险策略、治理策略）。支持确定性信任/风险状态（正常、受限、隔离、审核）。
  - **可观测性与审计**：最小栈包含资源指标、Agent 进展指标、决策轨迹、工具轨迹、数据谱系。审计记录为结构化、仅追加，支持确定性回放（但限于强制管道，而非推理内部）。
- **架构不变量**：
  1. 无副作用操作无需确定性策略决策允许就执行。
  2. 所有策略结果（允许/拒绝/延迟）在重新调度前记录于仅追加审计记录。
  3. 调度决策仅依赖可观测状态和预算，不依赖内部推理 token。
  4. 底层 OS 仍是硬件资源的唯一中介。

## 6. 主要结论与发现

- 传统 OS 抽象对 Agent 工作负载不完整，需要新的系统层来管理意图、决策谱系、工具中介和确定性治理。
- AOS 作为控制平面，将 Agent 变为一等实体，同时保持确定性强制、可审计性和安全。
- AOS 可以通过用户空间运行时、OS 扩展、分布式控制平面或部分接管 OS 职责等模型实现，且可映射到 Linux（cgroups、namespace、seccomp、AppArmor/SELinux、eBPF）和 Windows（Job Objects、Restricted Tokens、AppContainer、ETW）现有原语。
- 关键设计原则：推理与执行分离、默认拒绝、能力作用域化、所有工具调用必须经过中介、策略决策必须确定性并记录原因码。
- 无需完全替换 OS，而是渐进式集成。
