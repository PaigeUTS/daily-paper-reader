## 摘要
大语言模型（LLM）智能体正从请求-响应助手演变为长时间运行的软件主体：它们跨模型调用维护状态、分支子任务、等待外部事件、请求人工授权、生成工具，并执行必须能被恢复和审计的副作用。本文介绍Agent libOS，一个受库操作系统启发的LLM智能体运行时基座。Agent libOS运行在传统宿主操作系统之上；它不实现硬件驱动、内核态隔离或POSIX兼容操作系统。相反，它将智能体视为AgentProcess：一个可调度的执行主体，具有进程身份、父子谱系、生命周期状态、从AgentImage派生的工具表、类型化对象内存、显式能力、人工队列、检查点、事件和审计记录。其核心设计规则是：工具是类似libc的包装器；运行时原语是权限边界。文件系统访问、对象访问、休眠、人工审批、JIT工具注册和外部副作用均在显式能力和策略下，在原语边界进行检查。我们描述了设计、威胁模型、Python原型和面向安全的评估。当前原型实现了异步调度、命名空间本地对象内存、运行时集成的人工审批、一次性权限授予、每进程工作目录、shell和镜像注册原语、基于libOS系统调用代理的Deno/TypeScript JIT工具、文件系统/对象桥接工具、可注入的资源提供者基座、确定性演示、真实模型烟雾测试脚本，以及撰写时的123个回归测试。Agent libOS不旨在提高规划器准确性，而是展示了一个运行时基座，在该基座中，长时间运行的LLM智能体可以被调度、授权、恢复和审计，而无需将工具分发视为信任边界。

## Abstract
Large language model (LLM) agents are evolving from request-response assistants into long-running software actors: they maintain state across model calls, fork subtasks, wait for external events, request human authority, generate tools, and perform side effects that must be resumed and audited. This paper presents Agent libOS, a library-OS-inspired runtime substrate for LLM agents. Agent libOS runs above a conventional host operating system; it does not implement hardware drivers, kernel-mode isolation, or a POSIX-compatible operating system. Instead, it treats an agent as an AgentProcess: a schedulable execution subject with process identity, parent-child lineage, lifecycle state, a tool table derived from an AgentImage, typed Object Memory, explicit capabilities, human queues, checkpoints, events, and audit records. Its central design rule is tools are libc-like wrappers; runtime primitives are the authority boundary. Filesystem access, object access, sleeps, human approval, JIT tool registration, and external side effects are checked at primitive boundaries under explicit capabilities and policy.   We describe the design, threat model, Python prototype, and safety-oriented evaluation. The current prototype implements async scheduling, namespace-local Object Memory, runtime-integrated human approval, one-shot permission grants, per-process working directories, shell and image-registration primitives, Deno/TypeScript JIT tools over a libOS syscall broker, filesystem/object bridge tools, an injectable Resource Provider Substrate, deterministic demos, real-model smoke scripts, and 123 regression tests at the time of writing. Rather than improving planner accuracy, Agent libOS demonstrates a runtime substrate in which long-running LLM agents can be scheduled, authorized, resumed, and audited without treating tool dispatch as the trust boundary.

### 1. 核心问题与整体含义（研究动机和背景）

- **问题**：现有LLM智能体主要采用聊天循环加工具注册表架构，将工具调用即视为信任边界。这种方式对长时间运行的智能体（如需要跨调用维护状态、分支子任务、等待外部事件、请求人工授权、生成工具等）来说存在严重缺陷：**工具可见性与资源权限混为一谈**，导致间接提示注入、工具输出注入、混乱代理行为以及长期智能体权限应随时间变化而难以管理。
- **背景**：受操作系统启发（如进程、能力系统、阻塞设备、检查点与审计），作者认为智能体基础设施应当将操作系统类比应用于运行时边界。现有工作如MemGPT（虚拟内存）、AIOS（操作系统支持）、Voyager（技能积累）等部分触及，但Agent libOS聚焦于更窄的边界：模型面对的动作如何变为被授权、可审计的运行时操作。
- **整体含义**：提出一种新型运行时基座，使长期运行的LLM智能体能够像经典操作系统进程一样被调度、授权、恢复和审计，而无需将工具分发当作信任边界。

### 2. 方法论：核心思想、关键技术细节

- **核心思想**：
  - **智能体即进程（AgentProcess）**：每个智能体实例是一个可调度的执行主体，拥有进程ID、父进程谱系、生命周期状态、工具表、对象内存、显式能力、人工队列、检查点、事件和审计记录。
  - **工具是libc，运行时原语是权限边界**：模型可见的工具只是类似libc的包装器，实际访问资源（文件系统、对象、人工等）必须通过运行时原语，在原语边界执行能力检查、策略判定和审计。
  - **分离可见性、调用和权限三个阶段**：可见性由进程工具表控制，调用由ToolBroker检查，权限由原语管理器在能力和策略下检查。
- **关键技术细节**：
  - **AgentProcess**：支持spawn、fork、exec、wait、signal、pause、resume、exit。fork会衰减内存视图和预算，不继承父进程写文件权限；exec不自动授予目标镜像所需能力。
  - **AgentImage**：固定默认工具、系统提示、上下文策略、安全配置和所需能力，通过能力检查的镜像注册原语加载。
  - **对象内存（Object Memory）**：类型化、带能力保护的对象图，命名空间本地，名称不是能力。每个进程有私有命名空间`process:<pid>`，共享命名空间类似目录。物料化器在模型调用前将内存视图转为有限文本上下文。
  - **能力与策略**：资源包括对象ID、命名空间、文件系统路径、人类、shell策略、镜像注册表条目等。支持`always_allow`、`always_deny`、`ask_each_time`、`allow_once`策略，人工审批请求包含进程ID、原语、路径、SHA-256等，使用repr转义。
  - **Shell原语**：接收argv数组而非命令字符串，按词元化argv匹配策略（allowlist/blocklist），而非子串或shell语法。
  - **人类队列**：人类作为运行时对象，原语需要输入时进程进入WAITING_HUMAN，运行时调度器处理队列后唤醒进程。
  - **JIT工具**：TypeScript代码作为Deno模块，只有`syscall(name, args)`接口，Deno以无任何主机权限启动（--no-prompt，禁用network、env、run等），静态导入限制为jsr白名单。
  - **系统调用**：Deno工具通过LibOSSyscallSession调用文件系统、对象内存、人类、时钟、进程生命周期、shell、镜像注册等，每个系统调用经过调用进程的能力、策略、审计。
  - **检查点与审计**：检查点快照可重构运行时状态（不能回滚外部副作用）；审计记录在权限变更和副作用边界发出。

### 6. 主要结论与发现

- 主要结论：Agent libOS证明了一种不同的智能体运行时基座，其中**工具分发不是信任边界，运行时原语才是**。通过将智能体建模为进程，分离可见性与权限，使用能力系统、显式人类审批和审计，可以对长时间运行的LLM智能体进行调度、授权、恢复和审计。
- 核心发现：传统聊天循环架构将工具调用等同于主机资源访问，而Agent libOS的“工具是libc、原语是权限边界”设计规则令模型可以请求任何动作，但实际副作用受运行时原语控制，从而即使模型被欺骗，副作用仍需通过能力/策略/人工检查。
- 其他发现：对象内存使物料化器而非模型决定哪些进入上下文；人类审批队列可作为运行时设备；JIT TypeScript工具在沙箱（Deno）中仅有系统调用接口，无法绕过运行时权限。

### 7. 优点

- **设计理念新颖**：将操作系统进程、能力、阻塞设备、检查点等成熟概念系统性地引入智能体运行时，而非仅作为隐喻。
- **明确的威胁模型和安全设计**：分离可见性、调用和权限三个阶段，使能力检查点明确，确保工具可见≠资源访问权。
- **可测试的声明**：安全属性编码为123个可重复执行的回归测试，而非仅论文描述。
- **原型完整**：实现了从进程管理、对象内存、能力系统、人类队列、JIT工具、资源提供者基座到检查点审计的完整运行时，并提供CLI和确定性演示。
- **扩展性**：资源提供者基座可替换文件系统、时钟、shell后端，JIT工具支持TypeScript/Deno，未来可扩展更多提供者（网络、浏览器等）。

### 8. 不足与局限

- **不解决语义提示注入**：模型仍可能被恶意文档欺骗去请求危险动作，运行时仅能保证该请求仍受原语能力/策略/人工检查。
- **无内核级隔离**：JIT Deno沙箱不是正式生产级沙箱，更强场景仍需Docker、Firecracker或WASM。
- **策略引擎较小**：仅支持基本能力约束、人类权限策略、shell策略列表等，缺乏风险评分、配额、角色基人类权限、敏感度标签。
- **检查点不能回滚外部副作用**：一旦文件写出等外部操作完成，检查点无法撤销。
- **上下文管理初步**：工具结果压缩、长文档分页、重复动作抑制等未完善。
- **审计日志当前仅为记录流**，缺乏按进程、能力、资源等索引查询。
- **未进行端到端任务成功率评测**，缺乏性能、延迟和成本数据，也未与主流框架（AutoGen、LangGraph）对比。
